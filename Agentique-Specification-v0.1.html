01 / BUILD SPECIFICATION

Purpose and release boundary#

A system that builds systems, beginning with a modelling and simulation engine.

Agentique is an AI-assisted system modelling and simulation environment. A Human Operator works through the Console to describe, visualise and explore systems. The Rust Engine implements the supported KerML/SysML capabilities. The longer-term engineering loop connects those models to planning, implementation and verification.

Agentique itself is a system modelled in SysML, grounded in KerML. Its architecture and acceptance obligations accompany the implementation from the first milestone. Its modelling language does not dictate the technologies of the systems it will build.

Baseline versus decisions

Rust, the standards foundation, the two Console interfaces, self-modelling, and simulation are established project decisions. The bounded v0.1 execution contract and release scope below are proposed engineering decisions. “Must” defines a requirement of this draft; it does not claim that a capability already exists.

Release boundary

The first release must complete one trustworthy model–scenario–run–inspection loop. It is not a universal simulator or a complete system-construction toolchain.

Standards are the foundation#

Implement the languages; do not create another System metamodel.

The reference baseline is KerML 1.0, SysML 2.0 Part 1, and Systems Modeling API and Services 1.0, using the March 2026 publications identified below. [1][2][3]

Reference publications
ReferencePinned publicationRole in this specification
KerML 1.0formal/2026-03-01Language foundation and semantic libraries.
SysML 2.0, Part 1formal/2026-03-02System descriptions and supported execution semantics.
Systems Modeling API 1.0formal/2026-03-04Interoperable model-service contracts; not the simulator API.

Use the published semantic, data type, function and systems libraries rather than independent substitutes. Their publication references are included in standards.references.json; exact bytes, hashes and transitive dependencies must be locked at M0. [4][5]

Two uses of the standards

Agentique implements modelling capabilities defined by the standards. Agentique’s own design is also authored with them. The runtime may use Rust-specific representations, but each supported construct needs a tested semantic correspondence.

“System” is the role of a selected subject, not a new language primitive. In the self-model, Agentique is a part definition and agentique is its selected part usage. Packages, definitions, model ownership, subject composition and run occurrences remain distinct.

Report this release as based on KerML/SysML, with a published coverage manifest. Do not claim full conformance. The standards distinguish syntax, semantics and interchange obligations; a restricted runner or passing parser tests is insufficient. [1][2]

The execution contract may select a restricted class of models and declared inputs; it must not override standard-required behaviour. Before enabling a construct, document its full dependency closure, language rule mapping and executable test obligations. Conflicting assumptions block the feature, rather than defining a private meaning.

System architecture#

Logical parts first. Deployment is a separate implementation decision.

Logical responsibilities
PartResponsibility
ConsoleThe Conversation plus the Surface. Maintains an explicit project, model revision, selection and optional run context.
AssistantConverts intent into inspectable proposals and typed tool calls. It is a client of the Engine, not a semantic authority.
Modelling servicesParse, resolve, validate, inspect and modify standards-based models; prepare accepted revisions.
Simulation runtimePrepare a supported behaviour, maintain isolated run state, advance execution and record evidence.
Workspace and run storesPersist accepted model revisions, drafts, scenarios, checkpoints and traces, with stable identities.
Application boundaryAuthenticate the local session, validate requests, enforce approvals, coordinate persistence and publish updates.

Initially deploy one modular backend and one browser Console. The Engine remains usable as Rust libraries in tests and through a command-line interface without HTTP, a database, or an AI provider.

The Human Operator is outside Agentique’s boundary. An external AI provider is an integration dependency. A simulated agent in a model is distinct from the live Assistant operating Agentique.

Agentique models itself#

The self-model is a maintained engineering artifact, not a decorative diagram.

The starter package supplies four SysML source files: architecture, a request-lifecycle behaviour slice, requirements, and verification declarations. They must be independently validated before serving as parser or execution oracles. This document does not claim that validation has already occurred.

Self-model files
ArtifactPurpose
AgentiqueArchitecture.sysmlConsole, Surface, Assistant, Engine responsibilities and interface topology.
AgentiqueBehaviour.sysmlAn explicit state-and-transition description for one request lifecycle.
AgentiqueRequirements.sysmlThe numbered requirements below as documentary SysML requirements.
AgentiqueVerification.sysmlVerification obligations referencing those requirements; no executable verdicts yet.

Use the architecture model to guide component boundaries. Connect each requirement to its implementation module, acceptance test, relevant model revision and recorded outcome. A declaration or trace link alone must never count as evidence of satisfaction.

Before release, import, inspect and run the selected self-model slice through Agentique itself. Other tools may validate the model during bootstrapping. A running build may inspect a candidate successor, but cannot silently change its own authority or deployed binary.

Read the draft behaviour source
package AgentiqueBehaviour {
    doc /* AGQ v0.1 draft: one-request validation lifecycle.
       Scope: a behaviour slice of Agentique, not a model of the complete service.
       Syntax and semantics require independent tool validation at milestone M0.
       The runtime supplies scenario inputs to the input port; it does not run a validator here.
       Accepted and rejected are ordinary stable states, not SysML final states.
    */

    item def CheckRequested;
    item def ValidationPassed;
    item def ValidationFailed;

    state def RequestLifecycle {
        port input;
        entry;
        then idle;

        state idle;
        state checking;
        state accepted;
        state rejected;

        transition beginCheck
            first idle
            accept CheckRequested via input
            then checking;

        transition acceptCheck
            first checking
            accept ValidationPassed via input
            then accepted;

        transition rejectCheck
            first checking
            accept ValidationFailed via input
            then rejected;
    }
}
Model–implementation discipline

Record logical model elements against Rust modules and tests through trace links. Do not require a one-to-one model-element/Rust-struct mapping, and do not equate the self-model with the actual running implementation.

05 / BUILD SPECIFICATION

Modelling contract#

One accepted model, explicit revisions, no competing hidden copies.

Processing path: source → syntax tree → resolved semantic model → validation → accepted revision. Simulation preparation derives an executable plan from the selected behaviour. Plans and indexes are disposable projections with source mappings, not independently authored system definitions.

Identity: allocate stable model-element identifiers. Keep names and paths as locators. Distinguish a usage declaration from the runtime occurrences it can produce; runtime identity is qualified by run and occurrence, not just a declaration ID.

Editing: all semantic edits carry a base revision. Validate a candidate change set before an atomic commit. An invalid text draft remains recoverable without replacing the accepted model. Explicit rename/move operations preserve identity; ambiguous external text edits require identity reconciliation rather than silent reassignment.

Persistence and interchange: maintain an identity mapping with exported project artifacts; plain text alone must not be assumed to preserve all internal IDs. On import, resolve recorded identities or explicitly create a new model with a correspondence. Retain original unsupported source and prohibit lossy overwrite.

Validation: distinguish syntax errors, well-formedness failures, incomplete experiment bindings, unsupported capabilities and failed experiment checks. No missing value becomes zero, false or an inferred fact. JSON serialization and Rust type checking do not substitute for language semantics.

Authority for this revision

The maintained SysML requirements are the normative product obligations; the numbered HTML requirements are their reading view. The detailed execution and operation contracts supplement them. During this draft they are generated together; future CI must detect drift. Language meaning is governed by the pinned OMG references, following their own precedence rules.

Simulation contract · AGQ-SEQ-01#

A deliberately bounded first runtime, not an invented replacement semantics.

Executable scope: one selected flat, exclusive state region, its explicit initial succession, empty state entry actions, typed incoming item events, and guarded transitions with no effect bodies. Use finitely instantiated structure and complete initial bindings. Permit only listed pure Boolean/integer comparisons and Boolean operators. Evaluate Integer values exactly; implementation limits cause an explicit error, never wraparound or silent coercion.

Hierarchical subject structure remains modelled, but this release does not execute every contained behaviour. The prepared plan identifies the selected slice and all excluded interactions. Parallel states, elapsed-time triggers, continuous equations, dynamic spawning, arbitrary actions and live calls are outside this execution contract.

Experiment records — Agentique application contracts, not an alternative model language
ObjectRequired contents
Model revisionSource and semantic identities, selected behaviour, pinned library closure and validation result.
Scenario revisionComplete parameter bindings, ordered input deliveries, receiver references, stop condition and resource limits.
Prepared runResolved model/scenario revisions, Engine build ID, execution-contract version, input digest, plan digest and source mapping.
Run stateActive occurrences, bound values, next input ordinal, semantic-step counter, status, checkpoints and diagnostic state.
ResultsInput-delivery records, transition records, before/after snapshots, stop reason and separately reported checks.

Execution rules

Initialise: validate and bind the selected scope; construct fresh occurrences, perform the empty entry/initial succession and record the initial active state. No shared mutable runtime state may be retained between runs.

Advance: first evaluate the scenario stop condition. Otherwise deliver the next input in its explicit ordinal order to its resolved receiver. An input step records delivery, resolves eligible accepters and guards, and takes the single permitted transition to a stable target state. The implementation must demonstrate that this restricted step matches the relevant standard semantics.

Ambiguity: zero matching eligible transitions is unhandled_input; more than one is ambiguous_transition. Both block this experiment without selecting an arbitrary winner or calling the model invalid. A later execution policy may support richer semantics explicitly. Unmatched items are not silently dropped.

Step commit: compute a candidate step without changing the committed checkpoint. On ambiguity or error, retain the before-state and input cursor, record the diagnostic, and block. On success, persist input consumption, semantic state and trace records together before acknowledging the step.

Ordering: input ordinal and semantic-step index are logical order, not seconds. This contract promises no rates, physical durations or wall-clock synchronisation. Interactive input injection requires a new scenario revision and new run.

Control: run repeats steps; pause and stop acknowledge at a recorded safe point; step advances once while paused. Reset creates a new run from the same pinned inputs. Terminal records remain immutable. Duplicate control commands are idempotent; conflicting control versions are rejected.

Completion: a satisfied stop condition ends the run with condition_met. An exhausted input sequence without that condition ends with input_exhausted. An ordinary state with no outgoing transition is not automatically a SysML final state or a successful experiment.

Limits and errors: check input, memory, trace and step budgets before accepting work. Evaluation errors and exhausted budgets stop with explicit reasons. On interruption retain the last durable checkpoint. Do not silently resume a run with changed dependencies.

Reproducibility: compare normalized semantic traces, excluding run IDs and recording timestamps. With identical pinned inputs and Engine build, manual and continuous execution must agree. Record model state separately from recording time and from any later observation of a real implementation.

Simulation is isolated

No simulated operation may invoke a shell, network, external agent, builder or deployment endpoint. Future live integrations require a distinct mode, capability checks and visible identification. An Assistant explanation never creates a state transition.

Checks have not_run, pass, fail, inconclusive or error status; lifecycle status is separate. The starter documentary requirements have no automatic check implementation and must remain not_run.

07 / BUILD SPECIFICATION

Console and Assistant#

Conversation and visual interaction share selection, revision and run context.

The Conversation supports inspection, proposed model changes, scenario preparation, approved run control and explanations grounded in tool results. Messages referring to model elements retain their IDs and revision context, not only display names. Assistant answers distinguish requested actions, accepted changes and observed results.

The Surface is a Canvas of Views. The initial set is a structure tree/diagram, property inspector, selected behaviour graph and run timeline with state inspection. Provide a scenario editor and visible initialise/run/pause/step/stop controls. Each View displays its model revision and optional run identity.

Selection is shared between interfaces. Layout changes are presentation-only. Semantic drag, connect, rename and property edits produce Engine change proposals. Live runs remain pinned when the design changes; the Console offers a new run instead of rewriting the old one.

Support keyboard navigation, labelled controls, visible focus, readable contrast and table/tree alternatives. Keep diagrams bounded within their View; a large canvas must not make basic inspection inaccessible.

AI authority

The Assistant receives narrowly scoped tools, not direct database or runtime-memory access. Read-only tools do not require approval; semantic writes and run preparation/execution require a review bound to actor, base revision, exact payload and expiry. Approved controls may be delegated for that specific run. Read access remains subject to project scope.

Model-provider failure must not disable manual modelling or running an already prepared simulation. For acceptance tests, use a deterministic Assistant stub to exercise the tool contract; do not depend on a particular generated answer.

Operations and persistence#

Typed commands, explicit provenance, controlled change.

These are Agentique application operations, not claimed OMG endpoint names. Model interoperability is implemented through a separate adapter to the Systems Modeling API. Its official publication includes the service contracts and conformance test suite. [3]

Internal service boundary
OperationContract
InspectModelRead a revision-qualified selection. Return a projection with stable element references and diagnostics.
ProposeChange → CommitChangeReturn an inspectable diff and validation report; accept only the approved proposal against its unchanged base revision.
PrepareRunResolve a model revision, scenario revision and execution contract into an immutable plan or a complete diagnostic report.
ControlRunUse run ID, command ID and expected control version. Return the resulting status and committed checkpoint.
ReadRunPage trace records by sequence number; inspect state at a checkpoint without changing execution.
ExportProjectProduce the supported standard representation with digest, source revision and identity metadata.

Every mutation records actor, command ID, scope, payload digest and resulting revision or checkpoint. Repeating the same command ID and payload returns the prior outcome; reusing the ID with another payload fails. The server derives authority from authenticated context, not a caller-supplied role label.

Publish model and run updates with monotonic sequence numbers and reconnect cursors. A disconnected Console can resume from the last seen sequence without repeating mutations. Apply bounded buffering; never let slow clients stall the simulation indefinitely.

Persist model revisions, source/identity mappings, approved changes, scenarios, run manifests, checkpoints and traces. Commit the model revision and its audit event together. A checkpoint is acknowledged only after its associated state and records are durable. On restart mark any unfinished run interrupted.

Store secrets outside models and traces. Keep live AI transport separate from the simulator’s sandbox. The first backend binds to loopback and requires a local session credential; remote deployment, shared tenancy and live execution require another security design.

09 / BUILD SPECIFICATION

Rust implementation structure#

One workspace, small libraries, replaceable adapters.

Fixed: Rust for the Engine and backend. Proposed adapter choices: a browser Console in TypeScript/React; Axum/Tokio for HTTP; Serde for serialization; PostgreSQL/SQLx for persistence. These choices do not define the semantics and remain replaceable implementation decisions.

agentique/
  models/                 # Maintained SysML self-model
  standards/              # Artifact lock, libraries and coverage mapping
  crates/
    model/                # Stable IDs and standards-mapped semantic structures
    syntax/               # KerML/SysML parsing, source spans, source preservation
    semantics/            # Resolution, implicit relationships, validation
    workspace/            # Revisions, atomic edits, import/export
    simulation/           # Preparation, runtime state, stepping and traces
    application/          # Commands, approvals, orchestration of adapters
    server/               # HTTP/event streams; no language rules
    cli/                  # Headless modelling and simulation
  adapters/               # Storage and AI-provider implementations
  console/                # Conversation and Surface
  tests/                  # Language, simulation, API and acceptance fixtures

Dependency rule: model types are foundational; syntax and semantics operate on them; workspace and simulation consume validated structures; application orchestrates them; adapters depend inward. HTTP and provider types must not leak into the semantic or simulation crates.

Use typed domain operations instead of generic unchecked field patches. An internal graph or intermediate representation is permitted only with explicit mapping to the standard constructs and preserved source references. Selecting a parser must follow a spike on grammar ambiguity, diagnostics, recovery and identity-preserving editing.

Do not implement an unrelated state-machine language in JSON. Scenario JSON only configures experiments against identified SysML behaviour; the runnable structure must come from the resolved model. Use independent, standards-derived fixtures to avoid validating an implementation solely against itself.

For the responsiveness acceptance test, record a baseline machine with at least four logical CPU cores and 16 GiB RAM. Use a project with 1,000 user-authored elements plus the pinned libraries and a run bounded to 10,000 steps. Report actual input sizes, memory, step latency and pause/stop latency; these are acceptance targets, not measured results.

Build the engine before depending on its Assistant.

Acceptance experiment: load Agentique’s self-model and select agentique.engine.models.requestLifecycle. Bind the accepted scenario and step through idle → checking → accepted. Repeat with the rejected scenario to reach rejected. Both traces must originate from the parsed SysML transitions, not hard-coded state names.

Then repeat from the same immutable baseline to compare trace digests, run both scenarios concurrently to check isolation, and rename the selected model elements to prove that identity rather than display names drives execution. With no second input, the run must report exhausted inputs rather than inventing a validation result.

The provided JSON files are unresolved scenario templates. Preparation replaces paths with resolved element/receiver IDs, adds model/library/build revisions and digests, and creates a new immutable scenario/run manifest. They are not directly executable engine files.

What this experiment proves

It tests Agentique’s ability to model and simulate a limited part of itself. It does not prove the real validator is correct, the whole platform has been simulated, or that a simulated outcome matches a deployed implementation.

This is a build specification and starter model package—not a working simulator.

Remaining implementation decisions: parser library; precise internal graph layout; durable storage schema; Console rendering library; AI-provider adapter; and an independent validation tool. These are bounded engineering decisions, not permission to alter the modelling standards.
