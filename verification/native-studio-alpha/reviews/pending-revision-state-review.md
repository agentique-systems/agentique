# Pending revision and candidate response review

Independent code/state review, 2026-09-25, main checkout at `88a4b14` plus pending edits. Scope: native `actions.rs`, `updates.rs`, `app.rs`, `presentation.rs`, `agents.rs`, with bridge and platform lifecycle contracts read for context. No builds or semantic-runtime executions were performed. Line references describe the reviewed working copy and may move during integration.

## Findings

1. **P1 — A new view query can permanently strand a pending revision.** `actions.rs:151` retains requested revision B separately from visible A, but Dependencies (`actions.rs:663–686`) obtains A from the visible selection and overwrites the shared `scene_request` without resolving `pending_revision`. When B returns, `updates.rs:164` rejects its superseded request ID. When the dependency projection for A returns, `updates.rs:166–168` rejects its revision because B remains pending. No accepted completion clears B. The operator remains on A, with saved views/session persistence blocked, and no current request capable of finishing the switch. A committed revision fetch can suffer the same supersession. `agents.rs:72` can also fence a pending revision by assigning `scene_request = 0`; saved view opening does not immediately remove the previous agent return state (`presentation.rs:274–315`).

   Reproduce with a delayed projection: request B from A, select a still-visible A node, request dependencies before B arrives, then deliver both successful replies. Assert B either installs or is explicitly cancelled; there must be no unresolved pending target without an outstanding transition request. Separate durable revision transition identity from disposable lens query identity, or explicitly resolve/cancel the transition before another action supersedes it.

2. **P1 — Dismissing an agent view can discard a successful validation lifecycle update.** Validate stores its mutation response ID in `scene_request` (`actions.rs:759` vicinity). While validation runs, Dismiss agent view remains allowed; it clears `scene_request` in `agents.rs:72`. The successful `Output::CandidateView` mutation is then dropped by the query-ID guard at `updates.rs:290–291`. The bridge marks the mutation completed before that guard (`updates.rs:12–15`), leaving the UI in Working while the platform is Validated. The same shared response slot can lose the refresh needed after an unresolved commit error. This does not bypass platform authority, but the operator sees incorrect candidate state and may be prevented from committing until a later query happens to repair it.

   Reproduce: Working candidate → dependency view → Validate → dismiss agent view → deliver validation reply. Assert retained candidate phase becomes Validated, the restored world/selection stays intact, and no old projection replaces it. Process matching candidate lifecycle outcomes independently of whether their original lens request remains visible. Superseded presentation and authoritative lifecycle completion are different concerns.

3. **P2 — A durable commit followed by projection failure has no retained in-app retry target.** `updates.rs:322–330` retains a committed candidate and sets the new pending revision. If its projection fails, `updates.rs:65–66` drops the target; if scene construction fails, `updates.rs:187` does the same. Binding and history still describe the base revision, and `HistoryRefresh` is only requested after a successful scene swap (`updates.rs:208–210`). The candidate is Committed, so Commit/Validate/Cancel/Create actions are unavailable. Reopening the project can discover the durable branch head, but the ordinary review flow has lost the exact committed revision target needed for a retry.

   Inject a projection failure immediately after a successful commit receipt. Retain the durable receipt/target independently from view preparation, expose Retry loading committed revision, and refresh immutable project history even when displaying that revision fails. Assert no duplicate commit is attempted and that the new branch head remains discoverable without restarting or reopening the whole project.

4. **P2 — The new transactional scene-build check covers ordinary Projection only.** `updates.rs:183–192` rolls back when an ordinary projection cannot build. `Output::Comparison` (`updates.rs:246–251`), `Output::Candidate` (`updates.rs:264–286`) and `Output::CandidateView` (`updates.rs:300–311`) install their new DTO/lifecycle data before calling `rebuild()` and ignore its Boolean result. A rejected projection, ownership cycle, invalid graph pin or geometry failure therefore leaves the previous scene visible while active comparison/candidate data and status describe the new result. Candidate handling can overwrite the scene error with “Candidate revision ready for review.” `agents.rs:85–109` also treats restoration as successful when its scene fails to build.

   Feed each response path a projection with a duplicate identity or a failing saved layout. Assert the previously visible scene, projection and selection remain one coherent presentation; authoritative lifecycle phase may still advance independently. Display the rendering failure without replacing it with a success status. Stage the disposable scene and its matching projection before publishing them together.

## Limits

These are state-machine findings inferred from reachable action/reply sequences, not runtime reproductions. Existing checks of context equality and saved revision IDs alone do not exercise them. The agent return record does not copy candidate phase or commit authority; no direct authority rollback was found there. The principal defect is sharing one mutable scene request ID across disposable queries, revision transitions and lifecycle reconciliation. I did not find a separate ordinary same-project HistoryRefresh race after a successful swap: the serialized worker normally returns that history before a subsequently queued revision projection, while the previous binding remains active.
