# Independent review: shared dependency closure checkpoints

**No correctness blocker found in the three-file checkpoint optimization.** This is a source review of the working changes to `producer_closure_rebind.rs`, `sysml/source.rs` and `tests/unit/producer_closure.rs`. It is not execution or exact semantic equivalence evidence. Root owns the compiling tests and subsequent CI oracle.

`checkpoint_sharing_dependency` is an explicit narrower transport contract. It retains a `Weak<ProducerClosedDependency>` and requires exact allocation identity again at rebind. A separately minted capability over the same overlay and equal publication/context digests is rejected. Retaining the Weak allocation prevents its address from being recycled into an unrelated allocation while the checkpoint exists; upgrading is unnecessary because the receiving context owns the matching strong Arc. The unchanged full `checkpoint` API remains available for independently restored mounts. With no closed dependency, the new method falls back to that full representation.

The capability is not a caller-supplied accepted flag. `ProducerClosedDependency::new` checks the exact overlay/context, expected registry, compatible certificate, full closure and empty construction obligations. Project attachment checks the immutable dependency Arc and descriptor contract before storing the capability in the context. The language caller creates the mount through the accepted Systems facade. `SourceInputs::compile_with_history` already rejects a previous compilation unless project and `AcceptedSourceDependency` Arc match. Ordinary edits and predecessor-bound restoration share that dependency, so the changed caller is within the narrower contract.

The existing factored signature routine skips a record only when it is the actual same immutable dependency record. Association occurrences, ordered contributions, computation-search sets, derived navigation and failures each have their own exact sharing checks. Every local record remains hashed, even when its own storage happens to be shared between revisions. Local references and occurrences update both endpoint signatures; a new incoming carrier into a dependency therefore changes the dependency subject's signature. Local proof, contribution, search and output-support changes still contribute, including a disappeared detached output whose supporting input values are unchanged. A dependency output cannot acquire a local supporting subject without ceasing to be the same protected dependency material.

Possible-writer closure is not copied from the old certificate. Rebind still checks producer registry and static query context, adds changed signatures and pending obligations to the affected set, transports only evaluations with preserved reads, then calls certificate issuance on the current model. Newly applicable local producer subjects still begin Pending. The unchanged immutable-row shortcut applies only where the new exact mounted dependency certifies the subject and the old row contains no evaluated/read state. Skipping immutable hashing therefore does not grant a new writer an old closed mask.

The new differential test is meaningful: it compares exact certificates, affected subjects and retained/reopened evaluation counts against full checkpoint transport for both an unrelated addition and a newly matching incoming relationship. It then verifies rejection of an equal but separately minted mount while the full checkpoint still accepts that mount.

The bounded coverage gap is that the new test does not yet run the factored path through a disappearing detached **local** output, a proof/search-only local change, or a newly applicable local writer that changes a previously closed requirement. Existing tests cover these invariants on the full checkpoint path. Running analogous factored/full comparisons would guard future changes to the shared hashing routine. No bypass was found by inspection; these are recommended regression cases before final qualification, not a claim that tests already failed. The comment describing `audit_subject_signatures` as audit-only is now narrower than its shared helper's actual use; this is a documentation issue only.

At the integration lead's request, the reviewer subsequently added `shared_dependency_checkpoint_preserves_output_support_and_new_writer_obligations` immediately after the first new test. It uses an actual producer-closed dependency with a model-scope writer and a local derived output. Losing that output must reopen its original producer despite unchanged subject records; adding another local writer while preserving the output must retain the prior evaluation but reopen EffectiveTyping through the new writer's pending state. Both cases compare the factored and full certificate, affected set, retained evaluations and reopened evaluations exactly. The test is formatted; root will run it. A separate proof/search-only local delta is still outside these two new cases.

The previous accepted-code freshness proposal is historical after these production edits. It must not be applied to this tree. The old exact oracle proves source `a6e1f41d2b549a8be10a79dfa3ec786c090b65b3`; new successful producer tests, full real command/cold equivalence, runtime authentication and an independently reviewed freshness hash update are required for the new implementation. No accepted semantic/publication/library identity should change to accommodate a failed proof.
